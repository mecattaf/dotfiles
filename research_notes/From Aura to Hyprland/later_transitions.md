## Which desktop and interaction requirements survive independently of Aura, Views and Otto?

### Takeaway

The strongest concrete requirement is Chrome-quality navigation among persistent work contexts, showing which work needs attention. A compositor workspace, a Herdr workspace and a browser tab are different objects; the historical research never conclusively resolved which one the requested outer tab strip should represent.

### Cited Findings

- The October 6 roadmap quotes Tom calling Chrome's bar “unbeatable … dragging, tabbing,” saying Herdr gave him the same concept of Chrome tabs/sessions, and objecting to the premise that the only home was a compositor tabbed container: “it doesn't have layershell?” The synthesis chose workspace tabs, but its final questions still ask whether Tom means a workspace rail or window tabs inside a tile. Treat the interpretation as provisional. [Quoted intent](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/shell/ROADMAP.md:31), [Open question](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/shell/ROADMAP.md:187)
- The proposed strip showed Herdr labels and rolled-up agent status for visible projectors. The memo counted roughly 135 Herdr workspaces and only seven agents: mirroring every work session into a compositor workspace would produce noise. Detached sessions were meant to remain discoverable through Goto. “Colour” itself remained unresolved between agent state and stable identity. [Mapping](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/shell/ROADMAP.md:59), [Colour question](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/SYNTHESIS.md:68)
- **Herdr's reusable seam is independent of GPUI.** Prior research built an inactive subscriber from `herdr-client`/`herdr-protocol`, connected to an isolated Herdr 0.9.3, and received pushed snapshots of workspaces/agents/branches with `boot_id`. Inactive clients did not receive surfaces or control geometry. This is a historical recorded experiment, not re-run here. [Protocol precedent](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/herdr-gpui-precedent.md:18)
- **Focus is not a harmless display operation.** That precedent did not prove external control of a particular kitty projector; GPUI windows own separate client connections. Public Herdr focus moved other attached clients; the synthesis prohibits using it to mirror compositor focus and notes that focus can consume done-until-seen state. [Focus boundary](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/SYNTHESIS.md:47)
- **Session lifetime is already deliberately independent of UI lifetime.** Current Herdr unit has no dependency on `graphical-session.target`; `X-SwitchMethod=keep-old` preserves running PTYs across deployment. Any Hyprland/native-shell prototype must remain a client of that durable runtime. [Current unit](/home/tom/mecattaf/dotfiles/home/herdr.nix:100)
- **What can transfer from Chrome is behavior, not necessarily C++.** October's Views-on-Otto research found four independent link barriers (Skia coexistence/version, C++ ABI, Ozone connection) but reproduced Chrome width arithmetic through a 44-line transliteration matching 23,040 oracle layouts. It names closing-width freeze, reorder hysteresis, detach distance, motion guard and color policy as portable. Its claim that the only home was a compositor tabbed container was subsequently challenged by the user and later strip roadmap. [Extraction result](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/views-on-otto/SYNTHESIS.md:15), [Specific behavior](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/views-on-otto/SYNTHESIS.md:86)
- The October desk already largely comprised Chrome, kitty/Herdr and CLI helpers, with no resident bar or notification daemon. Research identified actual desktop holes but also invented scope: a full network/Bluetooth/calendar/plugin host failed its own week-three filter. The entire proposed cleanup/removal plan was contingent and must not be mistaken for completed changes. [Historical inventory](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/shell/gui-minimalism.md:16), [Rejected scope](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/shell/ROADMAP.md:168)

### Inferences

- Build a shell that projects existing state; do not create a second session manager. The natural composition is durable Herdr sessions + current Projects/Substrate entities + compositor surface/window identity. Each has its own authority. [Runtime independence](/home/tom/mecattaf/dotfiles/home/herdr.nix:100), [Project concepts](/home/tom/notes/references/continuity/2026-09-27-desk/2026-09-27/PROJECTS-CUBS-AND-SUNSET-2026-09-27.md:20)
- A workspace strip that looks like Chrome but cannot safely reorder, select the intended session or close only a view is not “Chrome quality.” The portable interaction policy must be paired with explicit lifecycle semantics; toolkit resemblance is insufficient. [Chrome behavior](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/views-on-otto/SYNTHESIS.md:86), [Focus caveat](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/herdr-gpui-precedent.md:26)

### Gaps

- No definitive later ruling found for left rail vs top strip; workspace vs grouped-window tabs; state colors vs identity colors. Proposed default: focus/raise an existing projector by stable identity, with detached work discoverable separately; closing a shell view never implicitly kills its Herdr session.
- No end-to-end evidence here for the historic helper-client “pre-target then spawn kitty” trick over today's remote Herdr path. It was tested on an isolated server only. Prefer direct supported targeting if current upstream has since added it.

## What historical GPUI findings matter to the new Hyprland/gpuix investigation?

### Takeaway

October's anti-GPUI conclusion was specific to layering GPUI beside Otto's own shell and private protocols. It is not a general rejection of GPUI on Hyprland. The crucial evaluation now is whether GPUiX exposes the GPUI and Wayland capabilities that a real desktop surface needs, independently of its familiar frontend syntax.

### Cited Findings

- Prior source-read research found upstream `WindowKind::LayerShell` and `LayerShellOptions` in the gpui-pre 0.3.8 snapshot pinned by GPUI Kit, real wlr-layer-shell v5 handling, layer-parented popup support, and a clock example. Thus “GPUI has no layer shell” was already corrected on October 6. [Historical source audit](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:21)
- That audit also found keyboard interactivity set only at creation, output-unplug TODOs, no session-lock/foreign-toplevel/ext-workspace in that backend, and no touch. These are specific historical API/backend observations that require current verification, especially for the Zenbook. [Capabilities and absences](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:25), [Touch](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:63)
- Its “keep Otto-kit” recommendation depended chiefly on Otto embedding part of its shell inside the compositor, Otto-only surface-style animation, a KDE-versus-ext blur mismatch, and maintenance cost of running two toolkits. Those rationales disappear or change when Otto is rejected. The memo itself identified GPUI Kit's richer tables, virtual lists, editor-grade input and Markdown as reasons to reconsider for dense data UI. [Conditional recommendation](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:7)
- The audit found several GPUI shell projects, all using forks/vendor/pins at the time; GPUI Kit's similarly named `gpui-shell` was a QuickJS plugin runtime feasibility baseline, not a desktop shell. Naming alone should never collapse these distinct layers. [Prior art](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:45)
- The GPUI layer-shell example built as a roughly 25.9 MB stripped Linux binary but was never run on Otto; the memo explicitly refused to turn that build into a performance claim. GPUI Kit's comparison availability marks were not performance measurements. [Build versus execution](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:119), [Comparison scope](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:59)

### Inferences

- Relevant technology questions for the new researchers: does GPUiX expose layer surfaces, stable IDs, focus/activation, input regions, popup grabs, fractional scaling, IME, accessibility and output lifecycle; can it consume Herdr pushed state without a second terminal runtime; can GPUI Kit Rust components be consumed through its binding or only reimplemented? Historical GPUI support does not establish GPUiX binding support. [Layer capabilities](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/gpui-as-alternative.md:25), [Toolkit-independent Herdr](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/herdr-gpui-precedent.md:20)
- Proposed default: Hyprland owns window management, existing services own work/session state, native clients own the small new interface; Chrome remains the browser. Port tested interaction policies where useful, not Views/Ash framework machinery. The current user's direction supersedes old toolkit preferences while keeping the demonstrated separation of responsibilities. [Reset](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes7/PRIMITIVES.md:5)
