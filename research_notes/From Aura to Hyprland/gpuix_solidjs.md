# GPUIX, SolidJS, and GPUI Kit: the native rendering replacement

Research snapshot: 2026-10-13. GPUIX source pinned to `6a5c7c142ac32f9eb0caefe0121be995cfc18631` (HEAD commit dated October 11); GPUI Kit to `c5f8eca4a0759f8c0c7ed624eddfd03f1c93a5f2` (October 13). Read-only documentation and source inspection. No application, compositor, install, build, or runtime test was run. The current user's declaration supersedes historical Aura/browser-engine requirements; historical assistant statements are not present constraints.

## Does GPUIX actually recover the earlier SolidJS idea?

### Takeaway
Yes: the correspondence is literal. An official Solid adapter already compiles Solid JSX into native GPUI mutations. It preserves TypeScript and fine-grained reactive authoring while replacing the historical browser-rendering assumption. It does not preserve the entire DOM/CSS component ecosystem.

### Cited Findings
- Historical March 16 discussion starts from Tom's Qt WebEngine/WebChannel shell on niri, SolidJS, and local SQLite. Later passages identify the desired family: launcher/search/dock, a local Linear/Trello-like task app, Superhuman-like email/calendar, one visual language, compositor-owned glass. This is primary evidence of intent; the surrounding assistant's claims and benchmarks remain historical assertions. [Local source](/home/tom/notes/references/devlogs/1h26/pre-sync/quickshellX-solidjs2-discussion.md:32).
- March 26 user explicitly describes fast local reactive shell plus potential mail/calendar/task applications and initially calls the Chromium choice a tension, not a fixed choice. In the same exchange another answer then explicitly requires HTML/CSS/JS in a browser engine. Preserve that evolution; the latest October instruction removes that requirement. [Local exchange](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:180).
- `packages/solid/src/universal.ts` imports `createRenderer` from `solid-js/universal`, implementing create/insert/remove/text/property operations over GPUIX host nodes. This is an actual adapter, not a proposed compatibility shim. [Pinned implementation](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/src/universal.ts).
- The package is version 0.10.0, Apache-2.0, with peer range `solid-js >=1.9 <2`; it uses Babel's Solid 1.9.15 compiler. Solid 2 from the old discussion is specifically outside that range. [Package manifest](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/package.json).
- Official Solid workflow: preserved JSX, `@gpuix/solid/preload` in Bun, `render(() => <App />)`, an exported Bun production plugin. No Vite needed for this path. Hot reload remounts on the existing window but loses signal state. Match adapter/native exact versions because pre-1.0 upgrades can break compatibility. [Solid guide](https://gpuix.dev/guides/solid).
- Native desktop uses napi-rs and GPUI; browser deployment is a separate wasm-bindgen backend. The native path is not a WebView. [Architecture](https://gpuix.dev/#architecture); [Native Cargo dependencies](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/Cargo.toml).
- The adapter retains event closures in JS, allocates host IDs, batches updates on microtasks, and flushes after dispatch. [Solid root](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/src/root.ts). The shared mutation queue still performs `JSON.stringify(queue)` before `renderer.applyBatch`; this is in-process native FFI, not zero-copy and not Chromium renderer-process IPC. [Mutation code](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/js/mutations.ts#L80).
- CSS-shaped properties are native style descriptions: spacing, dimensions, flex/grid, colors, outlines, structured shadows, hover/active/focus states. `gridTemplateColumns` is numeric here, not arbitrary browser CSS track syntax. [Style structure](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/src/style.rs#L146). README documents numeric spacing, unsupported CSS shorthand/calc strings, fixed positioning behaving like absolute, and explicit style properties rather than browser stylesheet semantics. [Supported styles](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/README.md#supported-styles).

### Inferences
- The architectural continuity is `TypeScript + Solid signals + local data + shared visual language`, not `Blink + DOM`. The sacred cow to discard is that web-developer productivity requires a browser engine.
- The old token values, material hierarchy, monochrome palette, spacing/radius/motion decisions can become TypeScript token objects. CSS custom-property files and DOM-oriented Kobalte/Tailwind components are not directly portable. Port the design decisions, not their former rendering machinery.
- Local SQLite remains a coherent app/backend choice, but no GPUIX database binding was verified here; keep data ownership separate from toolkit selection. This does not authorize adding interfaces to projects whose current product decision is backend-only.
- Since all native JS stays in the application process, this path drops Chromium's rendering process architecture and its browser capabilities. Memory reductions are plausible, but not measured here; the source still has JS host state, Rust retained state, JSON copying, GPU resources, and a JS runtime.

### Gaps
- No measured input-to-photon latency, resident memory, idle CPU, or startup result on the user's Zenbook. Historical 50ms motion settings are design intent, not verified GPUIX latency.
- No Solid 2 compatibility or effortless web-component reuse. No native CSS cascade/DOM/DevTools equivalence.

## Does the current implementation support a Hyprland shell surface?

### Takeaway
GPUIX already exposes wlr-layer-shell directly at its public TypeScript boundary and maps it into GPUI's Linux window type. The next task is validating shell behavior, not inventing the missing binding. A complete shell still requires compositor/service integration and lifecycle work.

### Cited Findings
- Public `LayerShellOptions` includes namespace, four layer choices, edge anchors, exclusive zone, exclusive edge, four margins, and keyboard interactivity. `WindowOptions` accepts `layerShell`, `appId`, and transparency. API explicitly says layer-shell applies on Linux/Wayland, not other backends. Focus/show options are documented as ignored on Linux. [Public API](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/index.d.ts#L663).
- Rust `to_layer_shell_options` maps these values; defaults are top layer, top/left/right anchoring, and no keyboard interaction. Linux conversion removes the titlebar and assigns `WindowKind::LayerShell`. Tests assert that mapping. Linux starts an in-process `gpuix-ui` thread with GPUI's event loop, a command channel, and the shared retained tree; events return via a nonblocking N-API ThreadsafeFunction. [Renderer implementation](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/src/renderer.rs#L1293), [window conversion](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/src/renderer.rs#L7408), [tests](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/src/renderer.rs#L8083).
- Cargo enables GPUI platform Wayland and X11. Its GPUI is the `remorses/zed` `gpuix` fork, pinned as submodule `c2e9f882030ca95cee55d206512a0a3ee6cd72b0`, not just an unspecified latest upstream crate. [Cargo](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/Cargo.toml#L47); [submodule declaration](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/.gitmodules); [pinned tree entry](https://github.com/remorses/gpuix/tree/6a5c7c142ac32f9eb0caefe0121be995cfc18631/zed).
- The pinned fork contains actual wlr protocol enum conversion and layer-shell options, including the unsupported-protocol error. [Wayland adapter](https://github.com/remorses/zed/blob/c2e9f882030ca95cee55d206512a0a3ee6cd72b0/crates/gpui_linux/src/linux/wayland/layer_shell.rs); [core options](https://github.com/remorses/zed/blob/c2e9f882030ca95cee55d206512a0a3ee6cd72b0/crates/gpui/src/platform/layer_shell.rs).
- CI builds GNU Linux x86_64 with Vulkan/wgpu dependencies. It deliberately disables Linux GPU test support pending image readback; functional test jobs target macOS and Windows. A Linux build entry is not proof of Hyprland shell acceptance. [CI](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/.github/workflows/ci.yml#L26).
- High-level Solid `render()` keeps a single global render slot and subsequent calls remount it. This is not a general multiwindow shell manager. Lower-level creation is exposed, but its safe multi-surface lifecycle was not validated. [Solid renderer](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/src/renderer.ts).

### Inferences
- A bar/dock/launcher can now be approached as a Solid GPUIX client surface while Hyprland owns desktop composition and window management. Separate processes per shell surface may be a simple starting point, but choosing that is future implementation work.
- Blur should remain a compositor policy on transparent native surfaces. The showcased GPUIX blurred-window example is macOS vibrancy, so it cannot establish Hyprland blur behavior.
- A first acceptance slice should be one native Wayland layer surface with stable namespace, reserved edge space, visible alpha, intentional keyboard focus, restart/close behavior, and correct scale on the actual seat. Then validate menus, clipboard/IME, multi-monitor placement, sleep/resume, and reconfiguration. Run compositor experiments only in runtime-test/disposable environment under workspace instructions.

### Gaps
- No output/display selector, changing layer options after creation, or surface input-region controls were found in the inspected public `WindowOptions` API. These are bounded API observations, not claims that underlying GPUI cannot implement them.
- Layer-shell enum mapping tests are not end-to-end compositor tests. No guarantee of correct hotplug, fractional scaling, popup grabs, Hyprland blur, screen lock, screen capture, system tray, D-Bus service integration, or remote GUI streaming follows from them.
- AppId and layer namespace are distinct identifiers. Use the layer namespace for layer-surface rule matching; do not treat the API's generic appId advice as proof a compositor matches layer rules by app_id.

## What is GPUI Kit, and does it compose automatically with GPUIX?

### Takeaway
GPUI Kit is Longbridge's Rust application toolkit, incorporating gpui-base and gpui-component. GPUIX is a separate TypeScript-to-GPUI renderer. They belong to the same broad rendering ecosystem, but they are not one already-integrated JavaScript toolkit.

### Cited Findings
- Current Longbridge README identifies `gpui-kit` as the umbrella dependency; `gpui-base` supplies behavior/state/infrastructure, `gpui-component` styled components, and optional `gpui-shell` hosts JavaScript extensions. GPUI Kit and gpui-component should neither be conflated as identical packages nor described as unrelated projects. [Project README](https://github.com/longbridge/gpui-kit/tree/c5f8eca4a0759f8c0c7ed624eddfd03f1c93a5f2).
- Kit workspace is version 0.7.3 and pins upstream snapshot crates `gpui-pre`/platform to exactly 0.3.9, with optional GPUI Fast 0.1.7. Its manifest cites a prior break from overly broad GPUI version ranges. This differs from GPUIX's pinned fork. [Kit manifest](https://github.com/longbridge/gpui-kit/blob/c5f8eca4a0759f8c0c7ed624eddfd03f1c93a5f2/Cargo.toml#L49).
- Kit's separate `gpui-shell` crate currently uses QuickJS/quickjs-jit, optional styled-component bindings, and has `publish = false`. It is a scriptable application host, not the Solid renderer identified above. [Shell manifest](https://github.com/longbridge/gpui-kit/blob/c5f8eca4a0759f8c0c7ed624eddfd03f1c93a5f2/crates/shell/Cargo.toml).
- Kit's comparison labels capabilities, not benchmark wins. It explicitly disclaims equivalent component counts and binary-size build conditions, has no substantiated cross-framework FPS ranking, and identifies native HTML as a restricted document renderer without general CSS/scripts. Wry integration is experimental; its Linux example is unfinished. [Comparison](https://gpui-kit.com/docs/comparison/).
- GPUIX's inspected Cargo manifest has no gpui-kit/gpui-component dependency. Its Solid package provides its own Button, Dialog, Select, Combobox, Tooltip, floating and motion exports. [Native dependencies](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/Cargo.toml); [Solid exports](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/package.json).
- GPUIX manifests declare Apache-2.0. Kit software is Apache-2.0; current documentation also offers eligible prose and illustrations under CC BY 4.0 with stated caveats. [GPUIX manifest](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/package.json); [Kit license explanation](https://github.com/longbridge/gpui-kit#license).

### Inferences
- Use GPUIX + Solid as the direct recovery of Tom's TypeScript authoring idea; use GPUI Kit initially as evidence of native widget possibilities and as a separate Rust toolkit/reference. Pulling Kit controls into GPUIX requires explicit bindings and GPUI revision reconciliation; a `<KitDataTable>` import is not established.
- The latest declaration legitimately retires Aura as a requirement without proving every Chromium-derived feature obsolete. Native productivity surfaces can proceed independently; any remaining browser-content requirement should be treated as a distinct browser application or explicit integration decision.

### Gaps
- No audited dependency-license bill of materials, stability guarantee, current npm-release parity, or headless Linux native-test availability beyond inspected source. Version numbers here describe the pinned source, not a verified installed package.
- No claim that Kit's performance figures predict Solid/GPUIX performance. No shared benchmark was run.
