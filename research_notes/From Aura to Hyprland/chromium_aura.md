# Chromium / Aura epoch: dated archaeology and what survives it

## 1. What did Tom actually want, and why did Chromium become the answer?

### Takeaway

The original objective was an exceptionally responsive, deeply system-integrated, agent-authored desktop whose interface Tom could change using familiar declarative tools. Chromium was a proposed means of obtaining that interaction and development model; the archive repeatedly promotes the means into a supposedly necessary architecture. Tom's latest instruction in this research session explicitly supersedes the entire Aura requirement and recognizes GPUIX as corresponding to the earlier SolidJS idea. Treat that as the controlling decision, not another candidate in an Aura comparison.

### Cited Findings

- **Direct Tom, March 26:** the initial alternatives request explicitly named CEF, Zed's GPUI, Servo and Nyxt. He wanted multiple serious alternative investigations, not a defense of his current implementation. The same chat explores a Neovim-like extensible core while retaining niri, kitty, Chrome and Nautilus. [Original chat](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:10)
- **Direct Tom, March 26:** his clarification was that QuickShellX existed because he wanted web technologies throughout the shell rather than a special frontend language. This was a genuine constraint at that time, rather than a requirement retrospectively invented by an assistant. [Clarification](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:175)
- **Direct Tom, March 26, especially important to today's SolidJS correction:** “I don't specifically need the chromium rendering engine” and “nothing is final here.” He associated SolidJS with a highly reactive layer shell, approximately 50 ms responsiveness, the feel of Linear, and eventually integrated mail, calendar and Trello-like applications. The desired property was flexibility and accessibility of interface construction as well as performance. He separately said the framework did not matter, though actual HTML/CSS/JS in a browser engine still mattered then. [Full question-and-answer context](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:189)
- **Direct Tom, March 26:** he rejected an assistant's WebKitGTK recommendation because reduced memory was not his objective; he asked for “the fastest shell in the world” despite using web technologies. It would misread history to describe this as merely a lightweight-panel project. [Performance correction](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:227)
- **Direct Tom, March 27:** after CEF/Electron/Rust debates, he selected a purpose-built native Chromium embedder, on the same architectural level as Electron and CEF. This was an explicit then-current choice. [Choice](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:567)
- **Direct Tom, March 27:** SolidJS/Kobalte may have been inherited from previous scoping rather than essential; React and Radix were acceptable. Later he supplied pi-generative-ui and morphdom as the generative-interface references, called the project “a new DOM,” rejected an artificial separation between static and generated UI, and chose a Proxy-backed observable graph as the starting kernel. [Framework reconsideration](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:658), [generative references and kernel discussion](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:684), [Tom's kernel response](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:791)
- **Assistant research, not Tom's technical proof:** the March GPUI artifact already identified native layer-shell support and gpui-shell targeting Hyprland/niri. It dismissed GPUI on the assumption that using it meant a complete Rust frontend rewrite, loss of TypeScript/SolidJS and slow iteration. Its final “if TypeScript/SolidJS, GPUI is architecturally irrelevant” conclusion is the precise historical premise today's GPUIX proposal reopens. Its performance and LLM-language-quality assertions are not demonstrated benchmarks and should not be repeated as facts. [March GPUI artifact](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/files/02-gpui-dark-horse.md:75)
- **Assistant architecture artifact:** the resulting March handoff proposed a roughly 5,000-line C++ Content API/layer-shell embedder plus a TypeScript Proxy/morphdom frontend, D-Bus events and niri IPC. It conceptualized the frontend as a projection of local system state and the LLM as its author. Its tiny implementation estimates and “mechanical” upgrade budgets are estimates, not receipts. [Architecture handoff](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/files/20-final-architecture-handoff.md:1)

### Inferences

- The lasting desire is better expressed as **declarative, reactive, comprehensible interfaces over real system state, with very fast visible response**, not “must own Aura.”
- “Web technology” historically bundled at least four wishes: TypeScript/Solid-style authoring, easy iteration, arbitrary rich content, and genuine browser compatibility. A native Solid renderer could answer the first three only to differing degrees; it is not automatically a browser engine. The synthesis should separate those properties instead of preserving Chromium as a proxy for all of them.
- Tom repeatedly challenged inherited framework choices himself. Today's supersession is consistent with that behavior, not a betrayal of a settled identity.

### Gaps

- Current GPUIX feature verification belongs to the separate technical research lane. Historical GPUI claims above establish what the March assistant believed, not what the libraries actually support today.
- The March transcript has been read in the principal architecture-decision spans, not every pasted third-party product page. The standalone GPUI artifact and core later decision documents were read fully.

## 2. How did the architecture actually evolve, and what was really demonstrated?

### Takeaway

This was not one steady path from Chromium to Aura to a finished desktop. Two independent decisions kept changing: **who owns composition/window management**, and **what renders the shell UI**. The archive contains real working prototypes and real DRM bring-up, but also repeated “settled” architectures, speculative cost estimates and draft implementation inventories that later summaries sometimes mistake for products.

### Cited Findings

1. **March: the COWL client model.** Chromium's Content API supplied real web surfaces; a custom Ozone layer-shell integration put them under niri. The shell could preserve ordinary external kitty and browser applications. The proposed local observable state graph was the central interaction concept. [March handoff](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/files/20-final-architecture-handoff.md:1)

2. **April: “Chromium is the compositor.”** An April 10 analysis enlarged COWL from a client into one root Aura tree per display, shell and external-app surfaces under that tree, Exo accepting Wayland clients, and Viz rendering the scene. Its attraction was one window model, integrated effects and direct control rather than asking another compositor through protocols. This document is an assistant proposal; some platform generalizations and effort estimates are overconfident. [April naming/architecture analysis](/home/tom/notes/references/devlogs/1h26/april-tmp/friday-apr10/compositor-deep-dive-pt3/05-naming-exo-aura.md:1)

3. **June 10: keep Ash rather than strip it.** The later June knowledge ledger records Tom vetoing “ship COWL under niri now, build compositor only when triggered” in favor of the keep-Ash/linux-chromeos compositor direction. This is a contemporaneous ledger attribution, not a freshly located verbatim user transcript. [Ledger](/home/tom/notes/references/devlogs/1h26/CADE/cade-june10/07-corpus/00-KNOWLEDGE-LEDGER.md:779)

4. **June 27: a genuinely functioning COWL web shell.** The end-of-day report records Chromium 149 with four live layer-shell surfaces: bar, workspace sidebar, launcher and Claude control UI. Sidebar collapse changed the actual exclusive zone; the launcher used app/calculator/command providers; the control UI handled Claude output and permissions. The report explicitly leaves real-hardware typing confirmation open, despite headless protocol/CDP checks. It also records live-versus-source D-Bus drift that could re-enable a crashing path. This was useful working software, not a complete reliable product. [Live surfaces](/home/tom/notes/references/devlogs/1h26/june27-cowl-nextsteps/REPORT-2026-06-27.md:12), [remaining keyboard proof](/home/tom/notes/references/devlogs/1h26/june27-cowl-nextsteps/REPORT-2026-06-27.md:115), [source drift](/home/tom/notes/references/devlogs/1h26/june27-cowl-nextsteps/REPORT-2026-06-27.md:189)

5. **June 27: the best performance lesson was mundane.** That report attributes the main toggle improvement to eliminating niri's approximately 120 ms retile animation, while COWL's hideSurface call was already 0.45 ms. It recommends keeping the Proxy kernel because replacing it with SolidJS would not fix the measured bottleneck. Reported idle PSS was 325 MB for bar+sidebar, CPU 1.9% of a core. These are local historical measurements, not a controlled comparison with modern GPUIX. [Performance report](/home/tom/notes/references/devlogs/1h26/june27-cowl-nextsteps/REPORT-2026-06-27.md:129)

6. **June 28–29: the native Views reversal.** CUBS's “conceptual pillars” explicitly drop the fear of C++, shrink web content to an agent canvas/settings, and advocate reusing Ash/Exo plus freedesktop services. The plan is native Views UI and native niri-like layout policy inside the compositor. It admits Fake clients make Ash boot rather than function and proposes substituting actual producers one by one. The June 29 SHELL-SHAPE-DECISION is still this compositor-owning architecture. [Pillars](/home/tom/notes/references/devlogs/1h26/CUBS/CONCEPTUAL-PILLARS.md:20), [boot distinction](/home/tom/notes/references/devlogs/1h26/CUBS/CONCEPTUAL-PILLARS.md:57), [native shell decision](/home/tom/notes/references/devlogs/1h26/CUBS/SHELL-SHAPE-DECISION.md:12)

7. **June 28–29: real bring-up, bounded proof.** The handoff records successful build, seated AMD startup and GBM initialization but initially no rendered display. The subsequent monitor report records the missing modeset caused by runtime ChromeOS checks, a constructor/init ordering error exposed by fixing them, and eventual real DP-4 5120×2880 modeset with animation. Thus “never got pixels” is false; equally, “Ash on generic Linux was fully functional” is false. [Initial proof boundary](/home/tom/notes/references/devlogs/1h26/CUBS/SESSION-HANDOFF.md:143), [eventual real modeset](/home/tom/notes/references/devlogs/1h26/CUBS/cade-drafts/m0/MONITOR-TEST-RESULTS.md:90)

8. **June 29 again: CUBS and CADE names become two distinct alternatives.** The steelman set explicitly chooses CUBS as native Views layer-shell client under niri, leaving CADE as the compositor-owning option. It reports dead mouse scrolling and a Nautilus launch crashing the Ash session. More importantly, the intended design already delegates layout to niri, so the single-scene/compositor assets were not being used. It says the bad interactive session confirmed the architectural mismatch rather than uniquely causing the decision. [Chosen fork](/home/tom/notes/references/devlogs/1h26/cubs-steelman/01-thesis-and-the-fork.md:22), [failure and rationale](/home/tom/notes/references/devlogs/1h26/cubs-steelman/01-thesis-and-the-fork.md:39)

9. **June 30: portable native shell plus browser instrument.** CUBS-DECISIONS codifies the niri-client interpretation while allowing sway/hyprland, emphasizes “the browser is an instrument; the shell is the point,” and makes niri/NixOS/account opt-in. It also admits the actual shell composition is not consolidated; one section revives a three-layer Mojo description despite the previous native-no-bridge rhetoric. These are overlapping decisions and unresolved design seams, not one perfectly coherent completed specification. [June 30 decisions](/home/tom/notes/references/devlogs/1h26/june30/CUBS-DECISIONS-jun30.md:1), [unconsolidated shell](/home/tom/notes/references/devlogs/1h26/june30/CUBS-DECISIONS-jun30.md:93)

10. **July 17–18: compositor ownership returns, with an appliance.** Tom's annotated decision list approves Agency owning scene/window management/shell while a tiny wlroots appliance holds DRM and displays its output. This is a third shape, neither the earlier direct-DRM Ash lift nor the niri client. The document's first “NO TABS” sentence is explicitly amended July 18: tabbed columns are in, browser windows may merge tabs, guest apps retain their own tabs. Anyone quoting “NO TABS ever” as final without the inline amendment would misread the source. These are scope approvals, not proof every feature shipped. [Annotated architecture and tabs](/home/tom/notes/references/archive/restructuring-history/midjuly-notes-reshape/july26-fable-second/july17-v1-annotation/00-DECIDE.md:21)

11. **August: continued Aura study, not proof of implementation.** The journal records saving sixteen Chromium design documents with local images and checking links. This establishes sustained investment in the Aura knowledge base. It does not establish a new working desktop milestone. [August journal](/home/tom/notes/journal/2026/08/04/scrape-and-save-chromium-aura-design-docs-as-local-markdown-files.md:14)

### Inferences

- The sacred cow is **unification by physical co-location**: if browser, shell, terminals, state and compositor share a binary or scene graph, coherence and responsiveness supposedly follow. The June 29 shell already achieved conceptual integration across a real niri boundary; the June 27 measurement also showed visible latency could come from animation policy rather than language/IPC.
- “Reuse mature Chromium” genuinely bought graphics, controls and browser machinery, but repeatedly expanded into owning service adaptation, input behavior, window management, security boundaries and Chromium maintenance. Calling those assets “free” hid which runtime assumptions still had to be rebuilt.
- Successful low-level bring-up did not require shipping that architecture. The steelman explicitly made this point in June; today's Hyprland choice is consistent with dropping nonessential ownership.
- The July apparatus and tabbed-column requirements are historical. They must not silently re-enter a new Hyprland plan after Tom's present rejection of Aura/CUBS.

### Gaps

- September/October retirement and compositor-layout changes are covered by the later-transitions researcher. This lane does not independently claim a final causal account for every later abandonment.
- No fresh benchmarks or builds were performed. Reported historical outcomes are explicitly attributed to their reports.
- The preserved monitor report's opening “still never modesets” headline is superseded by its appended success section. The handoff similarly becomes stale after the monitor test; read whole files, not first summaries.

## 3. What should carry into Hyprland / GPUIX, and what should be discarded?

### Takeaway

Preserve the human-facing interaction contract and portable data model; discard Aura ownership, Ash extraction, Exo hosting and a Chromium fork as requirements. The most valuable old abstraction is the typed stream of real work/session/system state and the recoverable workspace with provenance—not which renderer happens to display it.

### Cited Findings

- The June “reason CUBS exists” document describes **SignalSource** as any CLI/daemon emitting typed state and events to which surfaces bind. Its workspace is a captured concept: actual window grouping plus origin in a conversation, recoverable session and work evidence. It explicitly keeps content identity/lifecycle/snapshot and drops an application's private pane tree when the compositor already owns geometry. [SignalSource](/home/tom/notes/references/devlogs/1h26/cubs-steelman/04-reason-to-exist-capture-and-signalsources.md:43), [captured workspace](/home/tom/notes/references/devlogs/1h26/cubs-steelman/04-reason-to-exist-capture-and-signalsources.md:63)
- That same document then claims **only** a one-binary Chromium shell can combine a native session model, rich provenance canvas and CLI signals. This exclusivity is an architectural argument made by an assistant, not demonstrated impossibility of other compositions. It is the most direct sentence to retire under the sacred-cows heuristic. [Exclusivity claim](/home/tom/notes/references/devlogs/1h26/cubs-steelman/04-reason-to-exist-capture-and-signalsources.md:100)
- Native-first research already admitted iteration costs: imperative Views, manual subscriptions/invalidation, no hot reload, and gaps around declarative lists. It even noted ghostex moving toward Rust/GPUI partly for velocity. Thus the “native speed versus declarative ease” tension was visible before today's choice. [Costs](/home/tom/notes/references/devlogs/1h26/cubs-steelman/02-substrate-views-vs-web.md:144)
- The proposed material-glass effect was already decomposed into compositor blur plus translucent UI material levels, rather than inherently requiring HTML or Aura. The old analysis treated that decomposition as substrate-neutral. [Glass explanation](/home/tom/notes/references/devlogs/1h26/cubs-steelman/02-substrate-views-vs-web.md:124)
- **Primary technical boundary, verified now:** Aura provides window/event primitives; Ash is a consumer/shell rather than a synonym for Aura. Exo specifically implements a Wayland display server on top of Aura Shell. Ozone is the lower platform abstraction, with distinct Wayland-client and direct DRM paths. Views is the toolkit. These are separate capabilities; choosing a GPU UI toolkit cannot by itself imply compositor ownership or browser compatibility. [Aura overview](https://www.chromium.org/developers/design-documents/aura/aura-overview/), [Exo README](https://chromium.googlesource.com/chromium/src/+/HEAD/components/exo/README.md), [Ozone overview](https://chromium.googlesource.com/chromium/src/+/main/docs/ozone_overview.md), [Views README](https://chromium.googlesource.com/chromium/src/+/HEAD/ui/views/README.md)
- **Source-age caution:** the Aura web design docs still use old names such as RootWindow/RootWindowHost and discuss historical implementations. They are useful for responsibility boundaries, not authoritative instructions for a current fork. The current Ozone overview also contains visibly aged default/backend prose. Source code at a pinned revision would be needed for implementation-level claims. [Aura overview](https://www.chromium.org/developers/design-documents/aura/aura-overview/), [Ozone overview](https://chromium.googlesource.com/chromium/src/+/main/docs/ozone_overview.md)

### Inferences

- Proposed surviving interface shape: Hyprland owns windows, outputs, input policy and composition; a native reactive shell displays and controls its state and service state; existing browser/terminal applications remain actual clients; durable work/session state remains outside ephemeral surface processes.
- Translate the old invariant “keep the leaf, drop the tree” literally: preserve session/content identity, provenance, status and recoverability; do not copy Chromium tab collection or reconstruct an independent tiling tree as a surrogate for Hyprland.
- A unified command palette may remain useful, but shared search behavior does not require Chromium's AutocompleteController or browser process. Whether browser tabs participate depends on actual available integration and current user intent, not old CUBS ownership assumptions.
- GPUIX can be particularly relevant if it restores Solid-style authoring on a native renderer: it attacks the historical forced choice between web ergonomics and native UI. Its actual support and gaps must be established independently.
- Measure end-to-visible-response, stale-state behavior, input focus and crash/recovery. Old sub-millisecond method timings did not measure click-to-photon, and renderer labels alone did not identify the visible bottleneck.

Read principal Tom-authored decision spans in the March transcript and July17/18 annotated scope. **Unknowns and proposed defaults.**
- Unknown: which browser/document capabilities today must be embedded rather than opened in existing Chrome. Default: preserve existing browser surfaces until a concrete interaction requires embedding.
- Unknown: exact mapping between Hyprland windows/workspaces and durable Herdr/project entities. Default: one authoritative state owner per domain; derive the shell projection rather than duplicate ownership.
- Unknown: the proven GPUIX layer-shell, accessibility, text input/IME, multi-monitor/fractional-scale, lifecycle and service-integration behavior. Default: verify the smallest real interactive surface and recovery path before adopting an extensive shell parity checklist.
- Unknown: whether any old aesthetic or tab-management requirement still applies. Default: latest Tom correction supersedes Aura/CUBS; import only explicitly valuable behaviors, never dormant architecture wholesale.
