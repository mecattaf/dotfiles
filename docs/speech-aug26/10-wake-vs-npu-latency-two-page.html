Speech stack · latency note · 14 August 2026

Wake detection vs NPU Gemma

Where each belongs in the local speech pipeline on Strix Halo.

Decision

Keep the always-listening “Hey Jarvis” detector on CPU.

Use Gemma 4 E4B on the NPU only after wake-up, as an optional audio-understanding and fast-command branch.

The latency reason

Path Known timing Meaning
CPU wake detector OpenWakeWord scores every 80 ms; the sherpa verifier adds about 160 ms. Expected phrase-end-to-chime is roughly 250–500 ms on the proposed two-stage path.
Warm NPU Gemma E4B Measured text-only time to first token: 1.48 s. This is before audio preprocessing and generation. It is already slower than the whole wake decision budget.
Cold NPU Gemma E4B Measured startup: about 31 s. Cold/request-scoped execution is not an interactive speech path.

The primary path

CPU wake detector
        ↓ immediately
stream command into resident Parakeet
        ↓
Pi / Codex / Claude prepares the answer
        ↓
Qwen TTS renders and speaks

The wake stage is tiny, continuous, and latency-sensitive. A multimodal reasoning model is much larger than the job requires. Keeping wake detection on one CPU thread also leaves the GPU free for Parakeet and Qwen TTS, and the NPU free for work that can actually exploit semantic reasoning.

Routing and benchmark

Where NPU Gemma can win

Gemma E4B is interesting after activation because it can potentially collapse hearing and reasoning into one model. A completed command clip can go directly to a warm NPU session and produce either a short answer or a tool call.

command audio ─┬→ warm NPU Gemma → answer / tool call
               └→ Parakeet → smart agent → answer

During evaluation, these are parallel candidates—not serial stages. Running Gemma after Parakeet would add latency while duplicating understanding. The NPU route matters only if it returns a useful result sooner for a clearly defined command class.

Routing model

Workload Preferred route
Always-on wake detection CPU: OpenWakeWord candidate plus sherpa-onnx verifier.
General agent conversation Resident Parakeet → Pi/Codex/Claude → Qwen TTS.
Short, self-contained local commands Potentially warm NPU Gemma, if measured end-to-end latency wins.
Audio understanding or translation NPU Gemma is a useful specialist candidate.
Cold or request-scoped Gemma Exclude from interactive routing.

The decisive benchmark

A · command end → Parakeet final → first safe clause
B · command end → E4B audio → valid answer / tool call

Measure endpoint-to-first-useful-result, not model-only token speed. Include audio transfer, preprocessing, endpointing, decoding, validation, and the point at which playback can safely begin.

Promotion rule

  1. Keep Gemma warm during the benchmark; cold latency is already disqualifying.
  2. Run A and B on the same spoken commands and the same endpoint timestamps.
  3. Route a command class to the NPU only if B wins reliably and preserves answer/tool-call quality.
  4. Otherwise retain Gemma as an audio-understanding specialist, not a mandatory stage.
