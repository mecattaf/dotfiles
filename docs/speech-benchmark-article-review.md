# Reading the TinyComputers benchmark against this experiment

The useful lesson is to measure cold start and repeated generation with the model resident. The article's AMD CustomVoice/Eric results are RTF 4.20, 2.25, 2.56. They demonstrate a substantial first-run effect in that setup; they do not establish a universal 8060S speed limit. Our Base voice-cloning checkpoints, C++/Vulkan kernels and Q8 quantization differ from its PyTorch/ROCm CustomVoice path. [Article](https://tinycomputers.io/posts/the-real-cost-of-running-qwen-tts-locally-three-machines-compared.html)

**Warmup: observation supported; specific cause unproven.** Later runs are faster, but attributing the whole change to per-shape kernel compilation needs profiler/cache evidence. Initialization, library setup, allocations, dispatch, clocks and different generated sequence lengths are competing contributors. PyTorch's benchmarking guidance explicitly warms up and measures repeated executions; its GPU timing guidance requires synchronization. We should retain three resident repeats, report each generated duration and content coverage, and call the difference a first-run effect until a trace identifies its cause. [PyTorch benchmark guidance](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html), [GPU timing semantics](https://docs.pytorch.org/docs/2.9/notes/cuda.html#asynchronous-execution)

**Unified memory: useful capacity, insufficient explanation for this result.** Device tensors and their operation results stay on the GPU by default. KV caches and activations that fit on a discrete GPU do not inherently cross PCIe each decoding step. CPU control can cause synchronization and host/device copies, but the transfer volume and critical-path cost must be measured. GPU generation throughput cannot be explained from the bus generation alone. Our evidence should distinguish actual copy/transfer activity, kernel execution and CPU gaps. [PyTorch device semantics](https://docs.pytorch.org/docs/2.9/notes/cuda.html)

**BF16: distinguish storage, support, emulation and arithmetic.** A blanket “PyTorch promotes everything to FP32 on P40, therefore throughput halves” is not established by the published timings. In PyTorch 2.9.1, `is_bf16_supported(including_emulation=True)` can fall back to whether a BF16 tensor can be constructed; that says nothing about every operator's implementation or throughput. Inspect actual parameter/activation dtypes and dispatched kernels. FP32 intermediates in a particular attention implementation are a narrower documented behavior. [PyTorch 2.9.1 capability-check implementation](https://github.com/pytorch/pytorch/blob/v2.9.1/torch/cuda/__init__.py), [SDPA numerical behavior](https://docs.pytorch.org/docs/2.9/generated/torch.nn.functional.scaled_dot_product_attention.html)

**SDPA: a software operation with backend dispatch.** It is not a single hardware feature that a device either owns or lacks. PyTorch selects among fused and mathematical implementations according to inputs and support; the math path can upcast half/BF16 intermediates. Setting `attn_implementation="sdpa"` alone does not prove FlashAttention, AOTriton or any particular fused kernel executed. An eager-versus-SDPA experiment should preserve input, precision and decoding settings, then inspect dispatch before naming a hardware cause. [Official SDPA contract and dispatch controls](https://docs.pytorch.org/docs/2.9/generated/torch.nn.functional.scaled_dot_product_attention.html)

**F5: verify equal completed content before comparing service speed.** The reported 27.2s F5 output versus 197.5s Qwen output is a 7.26× duration difference despite the same-text description. That is not proof of truncation, but it prevents accepting an equivalent-narration comparison without transcripts and listening. Current F5 inference code has text batching, reference-based duration estimation, a speed parameter and fixed-duration control. Inspect the exact article revision/configuration, verify all batches were returned, and compare WER/coverage and speaking rate as well as RTF. A model that emits fewer correct words cannot win a read-aloud benchmark merely through a favorable ratio. [Article comparison](https://tinycomputers.io/posts/the-real-cost-of-running-qwen-tts-locally-three-machines-compared.html), [F5 inference implementation](https://github.com/SWivid/F5-TTS/blob/main/src/f5_tts/infer/utils_infer.py)

For this project, preserve first-request and warm timings, first playable audio separately from whole-output throughput, output duration, text coverage and voice quality. Sampled APU PPT is a package sensor, not a wall-power measurement; allocator, RSS and driver memory counters overlap. These measurements answer the user's workload without treating one published stack as the hardware's ceiling.
