# GPUiX restores the original SolidJS ambition

**The important discovery is that GPUiX reconnects with your original idea: one reactive, declarative way to build both a fast desktop shell and the applications you actually work in, while Hyprland owns the desktop underneath.** Your latest clarification settles the architectural question: this supersedes the whole Aura requirement. The March SolidJS proposal already included a launcher and dock alongside local Linear/Trello-style project views, Superhuman-style email and a calendar; it was never merely a nicer bar. Chromium became the route toward that experience, then gradually became an obligation to own the browser, UI toolkit and sometimes the compositor itself. GPUiX changes the premise that pushed those choices together: Solid-style interface authoring can target native GPUI rendering. The useful inheritance is the coherent work environment, recoverable sessions, shared components and precise interaction behavior. Aura, Ash extraction and a Chromium fork do not need to survive for those ideas to survive. ([March application scope](/home/tom/notes/references/devlogs/1h26/pre-sync/quickshellX-solidjs2-discussion.md:579))

## The original idea joined the shell to real applications

The earliest Agency sentence is strikingly direct: an interface for interacting with available agents and reviewing their task runs. The larger founding PRD puts persistent data in appropriate stores and treats interfaces as ways to work with that data. The center was already **ongoing work that you could understand, direct and return to**. Later corporate metaphors and platform strategies elaborated that goal; they should not be mistaken for the original requirement. ([Founding sentence](/home/tom/notes/references/archive/leger-labs/ai-org-chart.md:2), [Original PRD](/home/tom/notes/references/archive/leger-labs/unified-prd.md:1))

March 16 supplies the clearest missing connection. You described the Qt WebEngine/WebChannel shell under niri, considered SolidJS with local SQLite, and wanted the same components and aesthetic to support desktop controls and complete productivity applications. Your proposed method was practical: take the useful interface of an existing SaaS product and have AI reproduce it locally. You also corrected two assumptions that kept resurfacing: blur belonged to the compositor, not a glass-effect UI library; and increasingly elaborate animation was beside the point when you wanted an exceptionally responsive shell. The aspiration combined **frontend authorship, application depth and immediate interaction**. ([Initial stack question](/home/tom/notes/references/devlogs/1h26/pre-sync/quickshellX-solidjs2-discussion.md:32), [Application scope](/home/tom/notes/references/devlogs/1h26/pre-sync/quickshellX-solidjs2-discussion.md:579), [Blur correction](/home/tom/notes/references/devlogs/1h26/pre-sync/quickshellX-solidjs2-discussion.md:649), [Responsiveness correction](/home/tom/notes/references/devlogs/1h26/pre-sync/quickshellX-solidjs2-discussion.md:1541))

March 26 reinforces that reading: “I don't specifically need the chromium rendering engine” and “nothing is final here.” Actual web-engine compatibility mattered in that discussion, but Chromium itself was negotiable; the interface should feel as responsive and flexible as the products you admired. A contemporary assistant investigation dismissed GPUI because it supposedly meant giving up TypeScript/SolidJS and rewriting the frontend in Rust. **GPUiX directly attacks that old premise.** This is more consequential than finding another promising graphics library. ([Your clarification](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/chat.md:189), [Historical GPUI rejection](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/files/02-gpui-dark-horse.md:75))

By June, the work object had become clearer too. Your workspace linked window grouping to the conversation that originated it, recoverable sessions and signals from arbitrary CLIs. The accompanying synthesis called this capture: grouping, provenance, session and evidence together. July's service-backed application proposal then separated durable domain authority from replaceable presentation: services own data, validation, credentials and background work; interfaces own presentation and temporary view state; CLI and GUI are peer clients. It distinguished small ambient indicators from full applications, so an email badge need not drag an entire mailbox into a shell snapshot. That proposal was not a shipped platform, but its boundary fits the new direction unusually well. ([June workspace intent](/home/tom/notes/references/devlogs/1h26/cubs-steelman/CHAT-LOG.md:201), [July service/surface model](/home/tom/notes/references/devlogs/2h26/inbox-july23/agency-apps-service-backed-frontends.md:147), [Ambient versus interactive channels](/home/tom/notes/references/devlogs/2h26/inbox-july23/agency-apps-service-backed-frontends.md:176))

The scope should therefore remain a coherent graphical environment, with an ambient shell, navigable work contexts and substantial applications. Reducing it to an internal-URL index would miss the original idea. Equally, your May correction makes personal usefulness a legitimate destination: you were comfortable with a deeply capable, extremely niche tool that only you used. The historical enterprise pitch does not impose a present requirement to build a marketplace or general-purpose platform before the environment becomes useful. ([Personal-tool correction](/home/tom/notes/references/devlogs/1h26/kitty-harness/may20/08-thomas-additional-notes.md:8))

## The Aura epoch kept changing who owned the desktop

The history becomes intelligible once two questions are separated: **what renders the interface, and what owns windows and composition?** Aura provides window/event primitives, Views is Chromium's native toolkit, Ash is a shell built on that machinery, Exo hosts Wayland clients, and Ozone connects Chromium to underlying platforms. Those were different assets, not one indivisible answer. ([Aura overview](https://www.chromium.org/developers/design-documents/aura/aura-overview/), [Views](https://chromium.googlesource.com/chromium/src/+/HEAD/ui/views/README.md), [Exo](https://chromium.googlesource.com/chromium/src/+/HEAD/components/exo/README.md), [Ozone](https://chromium.googlesource.com/chromium/src/+/main/docs/ozone_overview.md))

March's COWL design was a Chromium Content API embedder acting as a layer-shell client under niri, with a reactive local-state frontend. April's analysis enlarged the idea: Chromium would become the compositor, with an Aura scene per display and external applications entering through Exo. By June, another turn favored retaining Ash and adapting its service assumptions. These choices promised mature behavior through reuse, but increasingly made your product responsible for display bring-up, input, service adaptation and compositor correctness. The escalation was real; the tiny engineering estimates accompanying it were proposals, not delivery evidence. ([March handoff](/home/tom/notes/references/devlogs/1h26/pre-sync/sync-march30/conv-chromium-fork-decision/files/20-final-architecture-handoff.md:1), [April compositor proposal](/home/tom/notes/references/devlogs/1h26/april-tmp/friday-apr10/compositor-deep-dive-pt3/05-naming-exo-aura.md:1), [June pillars](/home/tom/notes/references/devlogs/1h26/CUBS/CONCEPTUAL-PILLARS.md:20))

There was genuine working software. June 27's COWL report records four live layer surfaces: bar, workspace sidebar, launcher and Claude control interface. It also captures a particularly useful performance result: removing niri's roughly 120 ms retile animation mattered more to the visible toggle than replacing a frontend kernel whose hide call already took under a millisecond. The CADE/CUBS bring-up subsequently reached a real 5120×2880 display modeset with animation after correcting ChromeOS assumptions and initialization ordering. “It never produced pixels” would be false. “The desktop was therefore finished” would be equally false: the reports retained input and reliability gaps. ([Working surfaces and performance](/home/tom/notes/references/devlogs/1h26/june27-cowl-nextsteps/REPORT-2026-06-27.md:12), [Measured bottleneck](/home/tom/notes/references/devlogs/1h26/june27-cowl-nextsteps/REPORT-2026-06-27.md:129), [Successful modeset](/home/tom/notes/references/devlogs/1h26/CUBS/cade-drafts/m0/MONITOR-TEST-RESULTS.md:90))

June 29's steelman then separated the alternatives: CUBS as a native Views client under niri; CADE as compositor owner. Broken scrolling and a Nautilus-triggered session crash reinforced the split, but the deeper observation was architectural: the desired design already delegated geometry to niri, so owning the scene was not earning its cost. July nevertheless reopened compositor ownership through a small wlroots display appliance beneath Agency's own scene and window management. The tab model changed too: an initial “NO TABS” ruling was expressly amended to admit tabbed columns. The chronology is oscillation between implementation strategies around a persistent interaction goal, not steady completion of one immutable design. ([June fork](/home/tom/notes/references/devlogs/1h26/cubs-steelman/01-thesis-and-the-fork.md:22), [July annotated architecture and amendment](/home/tom/notes/references/archive/restructuring-history/midjuly-notes-reshape/july26-fable-second/july17-v1-annotation/00-DECIDE.md:21))

September's revision already demanded subtraction: reuse vanilla Chrome browser views, tabs, DevTools and settings rather than rebuilding them. The later Views-first pass reduced forty proposed Ash ports to five. October's Otto exploration found that sharing Skia did not make Views portable into another toolkit; a small part of Chrome's tab behavior was portable instead, with the width algorithm checked against 23,040 layouts. The subsequent Otto trial was real, but you rejected the result: frosting, animations and its file manager were not enough. These episodes leave useful interaction knowledge and engineering evidence; they do not leave an obligation to revive their projects. ([September reuse ruling](/home/tom/notes/references/continuity/2026-09-28-desk/2026-09-28/cubs-revision/REVISION-BRIEF.md:101), [Views-first reduction](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes5/views-first-rebalance.md:17), [Portable tab policy](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/views-on-otto/SYNTHESIS.md:15), [Otto rejection](/home/tom/notes/journal/2026/10/06/README.md:22))

The largest sacred cow was **coherence through common implementation**: the notion that the browser, shell, sessions and windows must share a process or renderer to form one comprehensible environment. A June assistant essay asserted precisely that exclusivity without proving it. Your current Aura supersession removes the assumption. The productive inheritance is shared identity, predictable interactions and consistent presentation across boundaries—not ownership of every mechanism behind them. ([Historical exclusivity claim](/home/tom/notes/references/devlogs/1h26/cubs-steelman/04-reason-to-exist-capture-and-signalsources.md:100))

## GPUiX makes the SolidJS connection literal

**GPUiX already has an official Solid renderer.** At the inspected October 11 commit, its adapter imports `createRenderer` from `solid-js/universal` and implements creation, insertion, removal, text and property changes against native host nodes. Native desktop rendering goes through napi-rs into GPUI; it does not put a WebView behind the JSX. This supplies the missing combination from March: TypeScript and fine-grained reactive authoring over a native interface. The supported peer range is Solid 1.9 through pre-2, so this recovers the SolidJS idea rather than validating the old discussion's specific Solid 2 choice. ([Solid adapter](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/src/universal.ts), [Package contract](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/package.json), [Architecture](https://gpuix.dev/#architecture))

It is familiar frontend authorship, with a different rendering contract. JSX and signals survive; the browser DOM, CSS cascade and arbitrary web-component compatibility do not. GPUiX accepts native style descriptions with familiar names, but does not implement general browser CSS. Your palette, spacing, typography, component behavior and interaction hierarchy can carry across; an existing DOM-oriented component library cannot simply be relabeled native. The development guide provides Bun compilation and hot reload, although reload currently loses signal state. The mutation bridge also serializes batches to JSON inside the process. These facts support an appealing architecture, not a claim of zero overhead or a measured speed victory on your Zenbook. ([Style contract](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/README.md#supported-styles), [Solid workflow](https://gpuix.dev/guides/solid), [Mutation bridge](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/js/mutations.ts#L80))

The desktop connection exists too. GPUiX's public TypeScript API exposes **layer-shell namespaces, layer selection, anchors, exclusive zones, margins and keyboard interactivity**. Its Linux conversion assigns GPUI's actual layer-shell window type, with mapping tests in source. Thus a native shell surface is not waiting for someone to invent the essential binding. Remaining work concerns application behavior and integration: output selection and dynamic surface controls are not fully exposed in the inspected API, and the high-level Solid `render()` uses one global render slot rather than providing a complete multiwindow shell manager. Those are concrete implementation questions, not reasons to return to Aura. ([Public window API](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/index.d.ts#L663), [Linux conversion](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/src/renderer.rs#L7408), [Solid renderer lifecycle](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/solid/src/renderer.ts))

GPUI Kit answers a related but separate question. Longbridge's current `gpui-kit` is an umbrella Rust toolkit containing `gpui-base` and styled `gpui-component`; its optional `gpui-shell` uses QuickJS and is not GPUiX's Solid adapter. GPUiX has its own components and no inspected dependency on Kit. Their GPUI revisions also differ: Kit pins snapshot crates while GPUiX pins its own Zed fork. **Kit widgets are not established as drop-in Solid components.** Kit is immediately useful as a component/interaction reference and a potential native donor; direct reuse requires an intentional bridge and compatible revisions. Its comparison page describes available capabilities, not a benchmark demonstrating that this proposed stack wins. ([Kit structure](https://github.com/longbridge/gpui-kit/tree/c5f8eca4a0759f8c0c7ed624eddfd03f1c93a5f2), [Kit versions](https://github.com/longbridge/gpui-kit/blob/c5f8eca4a0759f8c0c7ed624eddfd03f1c93a5f2/Cargo.toml#L49), [GPUiX dependencies](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/packages/native/Cargo.toml), [Comparison](https://gpui-kit.com/docs/comparison/))

## Hyprland supplies the desktop; Solid supplies your environment

Your latest clarification fixes the roles: **Hyprland for composition, animation and blur; Herdr plus kitty for terminals until Superlogical releases its terminal; Google Chrome for browsing.** This is an implementation direction, not another architecture-selection exercise. GPUiX/Solid builds the coherent shell and application surfaces around those primitives. There is no need to embed Chrome or kitty inside a GPUI widget to make their work part of the same environment.

Hyprland already exposes live window, workspace, focus and group events, JSON snapshots and operations to navigate and rearrange windows. Its groups provide selection and reordering within a window slot. A Solid surface can observe that state and invoke those operations; a custom compositor plugin is not inherent in the design. Layer-shell supplies the distinction between a panel that reserves space and an overlay that appears when needed, with explicit keyboard-interaction modes. Hyprland can remain the ordinary desktop foundation you intend. ([IPC](https://github.com/hyprwm/hyprland-wiki/blob/fde84d41b9a7154a5d211cfb1de50d5910791231/content/ipc/_index.md), [Group/window operations](https://github.com/hyprwm/hyprland-wiki/blob/fde84d41b9a7154a5d211cfb1de50d5910791231/content/configuring/core/dispatchers.md), [Layer-shell protocol](https://github.com/swaywm/wlr-protocols/blob/master/unstable/wlr-layer-shell-unstable-v1.xml))

The translation from the old concepts can stay concrete:

| Historical idea | New responsibility |
|---|---|
| One responsive shell and application language | Solid components rendered natively through GPUiX; shared design decisions across shell and apps. |
| Window arrangement, motion and background blur | Hyprland; shell surfaces request appropriate placement and transparency. |
| Left workspace rail, Goto and attention indicators | Native shell views combining live compositor state with existing work/session state. |
| A workspace remembers what produced it | Durable project/session/origin references associated with current windows; transient window IDs are not the record. |
| Rich terminal work | Herdr plus kitty, kept independently alive when the shell changes. |
| Web work | Google Chrome; a browser adapter only where a particular interaction needs browser-internal state. |
| Linear-like, email-like and other productivity surfaces | Full native applications over their actual services, using the same component language without moving service authority into the shell. |

This is the proposed composition, rather than a claim that those integrations are already implemented. The crucial detail is **what a tab represents**. A Hyprland group member is a window. A Chrome tab is internal browser state. A Herdr workspace can exist without any visible projector. A project or origin conversation can span all of them. The shell can present these together, but should not silently identify them with one another. Chrome exposes its tabs through its extension API, whereas Hyprland sees Chrome windows; compositor window identifiers are runtime references, not durable recovery keys. ([Chrome tabs](https://developer.chrome.com/docs/extensions/reference/api/tabs), [Hyprland identity implementation](https://github.com/hyprwm/Hyprland/blob/1bd31aaa579a40680ce876e1547e371b60c45522/src/desktop/view/window/WindowMetadata.cpp#L5))

Your October tab-bar discussion left that distinction unresolved: you praised Chrome's dragging/tabbing and Herdr's session model, then challenged the assumption that the interface had to live inside a compositor tabbed container. A sensible first translation is a work-context rail or overview that opens or focuses relevant views, with detached sessions still reachable. That retains the conceptual workspace without spawning a desktop for every historical session. Chrome's tested width, closing and drag policies remain useful wherever they fit; they do not decide the underlying work model. ([Your tab discussion and open question](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/shell/ROADMAP.md:31), [Portable policies](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/views-on-otto/SYNTHESIS.md:86))

Herdr already provides the right lifetime boundary. Its service deliberately survives compositor termination and preserves the running process across configuration switches. Historical isolated experiments also demonstrated toolkit-independent pushed workspace and agent snapshots. The interface should project that state, not recreate the session manager. Selecting a visible kitty projector should focus that view; it should not accidentally issue a shared Herdr focus command that changes another attached client or consumes an attention state. Closing the outer interface should never mean ending the work. ([Current Herdr service](/home/tom/mecattaf/dotfiles/home/herdr.nix:100), [Subscriber and focus evidence](/home/tom/notes/references/archive/2026-10-06-wm-scoping/notes8/otto-kit/herdr-gpui-precedent.md:18))

The same principle keeps the retired CUBS, workerd.nix and Cloudflare OS programs retired under your current rulings. Their useful concepts can inform surfaces over today's Projects/Substrate and services; they do not become prerequisites again. The July service/surface separation is particularly valuable here: a new frontend changes how you work with the system without requiring another replacement of its durable machinery. ([Service authority and replaceable surfaces](/home/tom/notes/references/devlogs/2h26/inbox-july23/agency-apps-service-backed-frontends.md:147))

## Prove the connected experience, then expand it

The first useful skeleton should demonstrate the concept across its boundaries: a native Solid rail and keyboard-invoked Goto, one real work context, its Herdr/kitty projector, a Chrome window and a small service-backed view. It should show state arriving, navigation reaching the intended window, an attention item opening the right work, and the interface disappearing and returning without losing that work. Reconnecting should reconcile current snapshots with durable context references rather than assuming an event stream was never interrupted. That is an architectural acceptance proposal, not a feature already supplied by the libraries. ([IPC observation/control boundary](https://github.com/hyprwm/hyprland-wiki/blob/fde84d41b9a7154a5d211cfb1de50d5910791231/content/ipc/_index.md), [Historical recoverable-workspace model](/home/tom/notes/references/devlogs/1h26/cubs-steelman/04-reason-to-exist-capture-and-signalsources.md:63))

Include one complete interaction in the application view—an actual query and meaningful reversible action—so the proof establishes the shared shell/application language rather than stopping at attractive status labels. Check typing and Escape, visible response, stale-state recovery, scale and the actual seat's input behavior. Measure the complete interaction rather than borrowing a renderer's benchmark or repeating the old mistake of timing only a fast method call. The outcome should answer whether this environment makes your work easier to enter, understand and continue. ([Historical timing lesson](/home/tom/notes/references/devlogs/1h26/june27-cowl-nextsteps/REPORT-2026-06-27.md:129), [Disconnected-implementation lesson](/home/tom/notes/references/devlogs/1h26/kitty-harness/may31/noon-verdict.md:132))

This research did not build or deploy that skeleton. Current source still declares Sway on the physical client and no physical desktop on Strix; changing that is a separate implementation/deployment step. Compositor experiments must preserve the live runtime through the repository's isolation wrapper or a disposable environment. ([Current display declaration](/home/tom/mecattaf/dotfiles/modules/display.nix:2), [Session-preservation instructions](/home/tom/mecattaf/dotfiles/AGENTS.md))

### Unknowns and proposed defaults

**Interaction identity remains the main product decision.** Default to durable work contexts associated with zero or more live views; keep group/window tabs as window operations and browser tabs as browser operations. Keep close-view separate from terminate-session. This preserves the original continuity requirement without making a compositor identifier into a new source of truth.

**GPUiX behavior on the actual seat remains unmeasured.** Source proves the native Solid path and layer-shell binding; it does not prove output hotplug, fractional scale, popup/focus behavior, IME, accessibility or latency in this environment. Default to a pinned GPUiX/Solid combination and a matching Hyprland API, then verify those behaviors in the connected skeleton. Use GPUiX's own components first; treat any GPUI Kit reuse as explicit integration rather than an assumed import. ([GPUiX Linux test limitation](https://github.com/remorses/gpuix/blob/6a5c7c142ac32f9eb0caefe0121be995cfc18631/.github/workflows/ci.yml#L26), [Version guidance](https://gpuix.dev/guides/solid))

**The broad application vision survives; individual application scope still follows current decisions.** A shared native component language does not authorize reopening retired products or adding frontends to services deliberately kept backend-only. Default to one useful existing service and one complete daily interaction, while keeping the architecture capable of the richer environment you originally described.
