Written for Tom to annotate. Answer inline on the `ANSWER:` lines (e.g. "a",

## Where things stand

- **The bar moved on 2026-07-31**: the final product must be fully featured,
  absorbing what Twenty CRM and the two reference command-line CRMs can do.
  The July 29 answers settled deals, pipelines, staleness, the audit table,
  enrichment, the servicing layer, and editing interactions.
- **An inventory pass was run over all three references** — the Go reference
  CLI, the TypeScript reference CLI, and the Twenty/sodimo-crm shape — listing
  every user-visible capability each one has.
- **Everything in those inventories was checked against what is already
  ruled.** Most of it is already decided one way or the other; the nine
  questions below are what genuinely is not. The last section lists what got
  classified as already-decided, so you can veto any of it.

## The 9 questions

1. **Tasks / next actions with due dates — IN or OUT?**
   Both reference CLIs have a task entity (title, due date, done, linked to a
   person or a deal). Sodimo-crm goes further and makes "every open deal must
   have a next action" the core loop of the product. Nothing has been ruled
   here — July 29 settled deals and pipelines, but tasks were only ever
   "deferred", never decided.
   (a) IN: a task is a title + optional due date + done flag, attached to a
       contact, org, or deal. Overdue is a query, not a daemon — nothing pops
       up or notifies you. *Recommended.*
   (b) OUT: a follow-up is just a line in an interaction summary, and you
       remember it yourself.
   ANSWER:
> OUT — tasks are externalized from the crm; I use an external mechanism to
> write them in my personal notes/backlog. (Tom, 2026-07-31)

2. **Tags across entities — IN or OUT?**
   Both reference CLIs have one shared tag vocabulary spanning contacts, orgs,
   deals and interactions, with tag-filtered listing. Sodimo-crm deliberately
   refused tags and used one free-text label on deals instead. You already
   have `category` on orgs and `relationship_hint` on contacts, which cover
   some of the same ground.
   (a) IN: tags on orgs, contacts, deals and interactions; one normalized
       vocabulary; filter any listing by tag. *Recommended.*
   (b) OUT: `category`, `relationship_hint` and pipelines are enough
       classification.
   ANSWER:
> OUT (Tom, 2026-07-31)

3. **Person-to-person relationships — IN or OUT?**
   The Go reference CLI lets you link two contacts with a type ("colleague",
   "referred by", "mentor") and shows the links from both sides. Neither of
   the other references has it. For a fundraise and a job hunt, "who
   introduced me to whom" is the intro-path question.
   (a) IN, contacts only: typed links between two contacts, visible from both
       ends, shown in the briefing. *Recommended.*
   (b) IN, contacts and orgs: also org-to-org links (portfolio, subsidiary,
       accelerator cohort).
   (c) OUT: the introduction lives in an interaction summary and the
       relationship hint.
   ANSWER:
> IN (Tom, 2026-07-31)

4. **`crm status` — a zero-argument front door — IN or OUT?**
   One command with no arguments printing counts (orgs, contacts,
   interactions, open deals), the date you last logged anything, how many
   contacts have never been contacted, and the database path it resolved. Both
   the Go reference CLI and Twenty have this; it doubles as the check that you
   are pointed at the right database.
   (a) IN. *Recommended.*
   (b) OUT: the staleness report and `ls` cover it.
   ANSWER:
> IN (Tom, 2026-07-31)

5. **Deal stage history — IN or OUT?**
   You ruled the general audit/events table OUT forever, with git history of
   the notes repo as the mutation audit. That ruling was about field-change
   logging. Separately: when a deal moves from one stage to the next, do we
   keep a row recording the move (from, to, when, and a note saying why)? Git
   history cannot answer "how long do things sit in first-meeting" because the
   database is a binary blob in the diff. Without this, only the current stage
   and the date it last changed exist.
   (a) IN: a narrow table of stage moves with real columns, including a note
       per move. This is deal data, not an audit log. *Recommended.*
   (b) OUT: keep only the current stage and the date it changed; the "why" for
       a move goes in an interaction.
   ANSWER:
> IN (Tom, 2026-07-31)

6. **Deal rot — flagging deals that have sat too long — IN or OUT?**
   Distinct from the contact staleness report you already ruled IN (that one
   is "nobody has talked to this person in N days"). This is "this deal has
   been stuck at this stage too long". Sodimo-crm sets the threshold per
   stage, so a slow stage and a fast stage rot at different speeds — which
   matters when one pipeline is a fundraise and another is a job hunt.
   (a) IN, per-stage: each stage carries its own "rots after N days"
       threshold, blank meaning never; one command lists what is rotting.
       *Recommended.*
   (b) IN, one global number: `--days 30` on a stale-deals command, no
       per-stage configuration.
   (c) OUT.
   ANSWER:
> IN (Tom, 2026-07-31)

7. **Canned report commands beyond staleness — IN or OUT?**
   Sodimo-crm ships a fixed set of named views: the pipeline board (deals
   grouped by stage), overdue actions, open deals with no next action, and
   "my day" (what is due today). The TypeScript reference CLI ships pipeline,
   activity volume, conversion rate and time-in-stage reports. Twenty does
   this with a saved-view builder, which is out of scope for a command-line
   tool either way.
   (a) IN, a fixed handful written by hand: pipeline board, overdue, deals
       with no next action, and recent activity. No view builder, no
       user-defined saved views. *Recommended.*
   (b) OUT: `status`, staleness and `ls` with flags are the whole reporting
       surface; anything else the agent computes on the fly.
   ANSWER:
> OUT — canned reports can be reconstituted ad hoc. (Tom, 2026-07-31)

8. **A general filter language on listings — IN or OUT?**
   The TypeScript reference CLI accepts expressions like
   `--filter "title~=CTO AND stage=proposal"`, and sodimo-crm has a richer
   version with date operators ("overdue", "in the next 7 days"). The
   alternative is fixed flags per entity (`ls deals --pipeline X --stage Y
   --tag Z`), which is what the frozen surface does today.
   (a) OUT: fixed, named flags per listing. Predictable, self-documenting in
       `--help`, and one less thing for an agent to get subtly wrong.
       *Recommended.*
   (b) IN: a general filter expression accepted by every listing command.
   ANSWER:
> OUT (Tom, 2026-07-31)

9. **Several emails / phones per contact — IN or OUT?**
   The one real fork in the data model. Twenty and the TypeScript reference
   CLI let a person hold a list of emails and phones (and match on any of
   them); the Go reference CLI and sodimo-crm allow exactly one of each. Real
   people have a work address and a personal one. Cost of allowing several:
   the duplicate-blocking uniqueness rule on email, which is currently a
   frozen non-negotiable, has to be rebuilt against the list.
   (a) OUT: one email, one phone, one LinkedIn per contact; a second address
       goes in the free-text context. *Recommended.*
   (b) IN: emails and phones become lists, and lookup matches any entry.
   ANSWER:
> OUT — one email/phone per contact; at best a note in the per-person context
> that the person has an additional email. (Tom, 2026-07-31)

## Ruled by this pass without needing you (veto any line)

Already IN:
- Import from the investor CSVs, duplicate detection, merge, export, the
  `/crm` skill, nix packaging (SPEC.md "Later (v0.2+)").
- Multiple named pipelines with their own ordered stages, plus commands to
  create and reshape them — you ruled several engagement types IN
  (DECIDE 07-29 q1), which needs more than one pipeline to exist.
- Deal outcome as open / won / lost with a free-text reason, and the date the
  stage last changed (follows from deals IN).
- Logging an interaction against a deal or an org, not only against contacts
  (follows from deals IN — otherwise deals have no history).
- A markdown export tree, one file per person with the timeline in prose, so
  `git log -p` shows what changed about someone in readable English
  (TRANSFER-BRIEF §8; "export" already IN per SPEC).
- Contact staleness / never-contacted report (DECIDE 07-29 q3).
- `unarchive`, `crm doctor`, editing interactions, terminal-table-or-JSON
  output (DECIDE 07-29 defaults + q7).

Already OUT:
- A general audit/events log of field changes (DECIDE 07-29 q4, "OUT
  forever").
- Money on deals, and therefore weighted forecasting, currency conversion and
  win-value reporting (DECIDE 07-29 q2, stage-only).
- Email sending, mailbox sync, calendar sync, LinkedIn scraping — external
  flows at best, never inside the tool (DECIDE 07-29 q5).
- Deadline trackers, cadence reminders, competitor watching (DECIDE 07-29 q6).
- Free-form custom fields as a key/value bag on any entity, and Twenty's
  runtime custom objects (TRANSFER-BRIEF §10: the JSON bag is the reason
  lookups degrade to full scans; sodimo-crm dropped the same engine).
- A second machine interface — no MCP server, no HTTP API, no filesystem
  mount (KNOWLEDGE.md; TRANSFER-BRIEF §10 on the mount).
- Web interface, kanban board screen, multiple users, permissions, sharing
  (single-user command-line tool; KNOWLEDGE.md).
- Workflow builder, webhooks, database triggers firing automations — the
  post-write shell hook is the whole automation surface (TRANSFER-BRIEF §8).
- Embedding / semantic search — the reference that advertises it does not
  have it; ranked full-text search is the ruled mechanism (SPEC.md,
  TRANSFER-BRIEF §4).
- File attachments as a managed store — transcript files under
  `notes/crm/transcripts/YYYY/` are the evidence of record (SPEC.md).
- Auto-creating a contact or org just because you referenced one that does not
  exist, outside a gated import flag (TRANSFER-BRIEF §8).
- Encryption of the database (KNOWLEDGE.md — the notes repo is private).

Engineering mechanics, not scope (these get built the right way without a
ruling):
- Notes stay a kind of interaction rather than a separate entity — the frozen
  schema already has `kind = note`.
- Short aliases, positional shorthand on `log`, prefixed references (`c12`,
  `o4`), the post-write hook, ids-only output for piping (TRANSFER-BRIEF §11).
- Where pipelines and stages are stored (database rows, edited through
  commands — not a config file; the only configuration is `$CRM_DB`).
- Small field additions that follow from the above (direction on an
  interaction, a note on a stage move, days-in-stage on a deal listing).
- Result limits, ordering and pagination on listings; batch operations via
  piping rather than batch flags.
