DF-MEM-3-1 is of the first kind but with no switch behind it: the row exists,
the shape is right, and the only thing missing is an authorisation this suite
does not hold. It is the reason MEM-3's oracle asserts on a scratch enqueue
directory rather than on the live one, and the reason the rows carry `argv []`
and `noEnqueue true` — so that the day the fence lifts, the worst an accidental
delivery can do is nothing.

DF-MEM-3-2 is a row about a validator's own scope rather than about an act. It
is written down because the number is uncomfortable and would otherwise be
discovered by whoever points the checker at the live events directory: 196 rows
in 600 that the daemon accepted, this checker refuses. Both refusals are for the
two keys MEM-3's mechanism requires of a harvest row, and neither is a type
error — the 600 rows carry no type violation at all — so the shape is right and
only its required set is deliberately stricter than the daemon's.

DF-CAP-1-2 and DF-CAP-1-3 are of the other kind, and are the same shape as each
other: both are cells whose only possible source is silent, and both are held
open by that silence rather than by any act this repository can take. Neither is
discharged by a fresh observation — a fresh UNKNOWN is still UNKNOWN — and
neither may be closed by deriving a number, which is the whole content of H-16,
"absent cells stay unknown and never headroom". DF-CAP-1-3 carries one extra
consequence worth naming: the day the endpoint answers, CAP-1's own oracle
clause asserting `model_split.opus == "UNKNOWN"` becomes wrong, and it is the
assertion that must move, not the row.
